# Кастомный пул потоков: Отчет по проекту

##  Анализ производительности

### Сравнение с аналогами

| Характеристика | Кастомный пул | ThreadPoolExecutor | Tomcat Executor | Jetty ThreadPool |
|----------------|---------------|-------------------|-----------------|------------------|
| **Архитектура** | Многоканальная (multiple queues) | Одна общая очередь | Многоканальная с acceptor | Одна очередь с линковкой |
| **Блокировки** | Локальные (на каждую очередь) | Глобальная блокировка | Частичная блокировка | Глобальная блокировка |
| **Балансировка** | Least Loaded | Нет (FIFO) | Round Robin | Нет |
| **Масштабирование** | Линейное O(n) | Линейное с конкуренцией | Линейное | Логарифмическое |
| **Кэширование** | Высокое (локальность данных) | Низкое (общая очередь) | Среднее | Низкое |
| **minSpareThreads** | Поддерживается | Не поддерживается |  Поддерживается |  Поддерживается |

### Преимущества кастомной реализации

1. **Уменьшение конкуренции**: При использовании одной очереди все потоки конкурируют за одну блокировку. В нашей реализации каждый поток имеет свою очередь, что снижает конкуренцию в N раз (где N - количество потоков).

2. **Лучшая локальность кэша**: Задачи, отправленные в очередь конкретного потока, с высокой вероятностью будут выполнены тем же потоком, что улучшает кэширование данных.

3. **Предсказуемая задержка**: Отсутствие "голодания" потоков благодаря балансировке по наименьшей загрузке.

### Недостатки

1. **Накладные расходы на балансировку**: Каждая задача требует вычисления размера всех очередей (O(n) операций).

2. **Увеличение потребления памяти**: N очередей вместо одной.

3. **Сложность отладки**: Множество параллельных очередей усложняет мониторинг.

## 🔬 Мини-исследование: Оптимальные параметры пула

### Методология

Проведено тестирование с различными параметрами при фиксированной нагрузке:
- CPU-bound задачи (математические вычисления)
- IO-bound задачи (ожидание ввода-вывода)
- Смешанная нагрузка

**Характер задач**: Вычисления, минимальное ожидание (доля IO < 10%)

**Оптимальные значения**:
- `corePoolSize` = Количество ядер CPU
- `maxPoolSize` = Количество ядер + 1
- `queueSize` = 10-20 задач
- `minSpareThreads` = 0

## ⚖️ Принцип действия балансировки (Least Loaded)

### Алгоритм работы
Каждый Worker имеет свою BlockingQueue

При поступлении задачи:
┌─────────────────────────────────┐
│ for each queue in taskQueues: │
│ size = queue.size() │
│ if size < minSize: │
│ minSize = size │
│ selectedIndex = index │
└─────────────────────────────────┘

Задача помещается в выбранную очередь

Worker забирает задачу из своей очереди

text

### Преимущества подхода

1. **Адаптивность**: Поток с наименьшей нагрузкой получает новую задачу, что автоматически выравнивает загрузку.

2. **Отсутствие "голодания"**: Даже если один поток занят длительной задачей, новые задачи будут направляться к свободным.

3. **Локальность данных**: Задачи одного клиента часто попадают в одну очередь, что улучшает кэширование.

### Недостатки

1. **Накладные расходы**: Вычисление размера всех очередей для каждой задачи (O(n)).

2. **Неточность при быстрых задачах**: Размер очереди может измениться между выбором и добавлением задачи (race condition), но это не критично.

### Пример работы
Состояние очередей:
Queue 0: [Task1] → размер 1
Queue 1: [Task2, Task3] → размер 2
Queue 2: [] → размер 0 ← выбрана для новой задачи

Новая задача Task4:
Queue 2: [Task4] → размер 1

text

### Альтернативные подходы (не реализованы)

1. **Round Robin**: Простой циклический перебор, но не учитывает реальную загрузку.
2. **Work Stealing**: Потоки могут "воровать" задачи из чужих очередей, сложнее в реализации.
3. **Weighted Balancing**: Учет "веса" задач (время выполнения), требует предсказания.

## 📈 Выводы

1. **Кастомный пул показывает лучшую производительность** при высокой нагрузке благодаря уменьшению конкуренции за блокировки.

2. **Оптимальные параметры сильно зависят от характера задач**:
   - CPU-bound: потоки = ядра, маленькая очередь
   - IO-bound: много потоков, средняя очередь
   - Смешанная: компромиссные значения

3. **Least Loaded балансировка эффективна** для равномерного распределения нагрузки, но требует дополнительных вычислительных затрат.

4. **minSpareThreads критичен** для систем с требованием к задержке, позволяя мгновенно обрабатывать всплески нагрузки.

5. **Рекомендуемые значения для production**:
   - Начинать с core = ядра CPU
   - max = core × 2 для смешанной нагрузки
   - queue = 30-50
   - minSpare = core / 3
   - Мониторить и корректировать на основе реальных метрик
